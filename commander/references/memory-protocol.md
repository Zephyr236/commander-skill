## 设计目标

用户需求原文：「还需要包含长期的记忆系统，记忆系统就是一个文件夹，主要是给指挥官使用，
里面存放了指挥官自己维护的记忆」

「获取记忆也是由一个独立的agent完成，在记忆文件夹中寻找指挥官需要的内容，
也寻找已经尝试过的方案，让整个任务能长时间的在指挥官的协调下完成。」

三个目标，按重要性排序：

1. **不重复踩坑** —— 记下失败及其条件，这是最高价值的一类记忆
2. **跨会话continuity** —— `/loop` 只有 7 天寿命、会话关掉就停，
   所以**状态必须在文件里**，记忆就是那个文件
3. **可解释的检索** —— 指挥官要能直接读懂命中的原文，而不是拿到一堆相似度分数

## 五类记忆

| 类型 | 目录 | 记什么 |
|---|---|---|
| `facts` | `memory/facts/` | 已验证的事实。结论 + 证据路径 |
| `attempts` | `memory/attempts/` | **试过的方案**：做了什么、结果、为什么、何时可再试 |
| `decisions` | `memory/decisions/` | 决策记录：选了什么、放弃了什么、理由 |
| `entities` | `memory/entities/` | 项目/系统/人的实体卡 |
| `journal` | `memory/journal/` | 按日期的指挥官日志 |

## attempts 是最重要的一类

绝大多数多智能体系统只记"做成了什么"。但**失败的信息量更大** ——
它排除了搜索空间，而且如果不记，下次会用同样的理由再试一遍。

所以 `attempts` 有两个**强烈建议填**的字段（CLI 里可选，但漏了这条记忆的价值会打折）：

- `why` —— 为什么（不）成立。不是"报错了"，而是"因为 X 机制，Y 条件不满足"
- `retry_when` —— **什么条件下可以再试**

`retry_when` 是防止指挥官对同一个坑无限重试的关键。没有它，
半年后的指挥官看到"连接池方案失败"还是不知道现在能不能试。

### 命令形式

```bash
./.commander/cmd memory attempt "用连接池降低 P99" \
  -a "把 max_pool_size 从 5 提到 50" \
  -o "P99 反而上升 30%，P50 不变" \
  -s failed \
  --why "连接数上去后 DB 侧锁竞争加剧，热点行争用变严重；瓶颈不在连接数而在热点行" \
  --retry-when "DB 侧完成读写分离且热点行拆表之后；或改为对热点行做批量合并写" \
  --tags 性能,连接池,反效果
```

### 什么时候写 attempts

- 派发失败且原因**非显而易见**时（参数错这种不用记）
- 一个方案验证下来"此路不通"时
- 走通了一条**不常规**的路时（`-s success`，同样有价值 —— 下次直接复用）

判断标准：**如果未来的我会想再试一次，就必须记。**

## 文件格式

一条记忆 = 一个 markdown 文件，YAML frontmatter + 正文。

```markdown
---
name: 连接池方案在热点行场景下反而更慢
type: attempts
tags: [性能, 连接池, 反效果]
status: failed          # success | failed | partial | open
confidence: high        # high | medium | low
related: [db-lock-contention]
date: 2026-09-28
---

# 连接池方案在热点行场景下反而更慢

## 尝试的做法

把 max_pool_size 从 5 提到 50 ...

## 结果

P99 反而上升 30% ...

## 为什么（不）成立

...

## 什么条件下可以再试

...
```

- **一个文件一条记忆** —— 便于独立更新、独立引用、`rg` 精确命中
- 文件名由 `name` slug 化而来，中文保留
- 同名不覆盖，自动加时间戳后缀（**历史不可变**）

## 检索机制

**结构化索引 + grep/ripgrep**，不做向量检索。理由：

| | rg 方案 | 向量方案 |
|---|---|---|
| 依赖 | 零（`rg` 可选，没有就退化为 Python 扫描） | embedding API + 向量库 |
| 成本 | 免费、毫秒级 | 每次写入要调 API |
| 可解释 | 指挥官直接读命中原文 | 只有相似度分数 |
| 适合规模 | 几千条以内 | 上万条 |

对"避免重复踩坑"这个目标，**能读到原文**比召回率高更重要。

### 命令

```bash
./.commander/cmd memory search "连接池"                    # 关键词
./.commander/cmd memory search "" -k attempts --status failed   # 只看失败尝试
./.commander/cmd memory search "" --tag 性能 -n 50         # 按标签
./.commander/cmd memory search "锁竞争" --full             # 打印正文
```

**排序规则**：失败 > 部分成功 > 成功 > 未定，同状态按日期倒序。
失败的排最前 —— 那是最该先看的。

### 索引

`memory/INDEX.md` 由 `./.commander/cmd memory index` 生成，是全库总览。
`patrol` 会检测索引是否落后于记忆文件并提示重建。

## memory-scout 的用法

`memory-scout` 是 `.claude/agents/memory-scout.md` 定义的独立 subagent：
工具限于 `Read/Glob/Grep`，**只读 `memory/`**，不写。

它的输出被要求是四段式：

1. **相关事实** —— 已验证的结论
2. **已尝试的方案** —— 成功与失败的都要，附 `retry_when`
3. **建议避免的路径** —— 依据是什么
4. **引用文件路径** —— 便于指挥官自己复核

### 什么时候派它

- 任何非平凡任务**开始前**
- 一个方案连续失败两次之后
- `/loop` 醒来发现任务卡住时

### 派发形式

```
派 memory-scout 查：<方向/技术/问题> 以前有没有试过？失败在哪？什么条件下可再试？
```

不要自己 `grep memory/` —— 那会占用指挥官的上下文，且容易漏掉标签维度。
这个 agent 存在的意义就是把检索的噪音挡在指挥官之外。

## 维护节奏

| 时机 | 动作 |
|---|---|
| 每次派发收尾 | 有非平凡发现就写一条 |
| 任务完成 | `memory index` 重建索引 |
| `patrol` 提示索引落后 | `memory index` |
| 每轮 loop | 检查有无该记未记的（`patrol` 的 warn 项会提示） |
| 记忆库为空 | 长任务开始前尤其危险 —— 说明没有历史可依 |

**反模式**：把记忆当日志写。记忆是**结论**，不是过程记录 ——
过程记录在 `agents/<id>/logs/` 里，那里才是流水账该待的地方。
