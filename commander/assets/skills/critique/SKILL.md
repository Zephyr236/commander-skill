# 对抗性审查

你的任务是**找出问题**。如果一个方案交给你审查后原封不动通过了，
那你多半没认真审。

## 原则

1. **默认方案有问题**。你的工作是找到它，不是确认它没问题。
2. **攻击隐含假设**。方案里没写出来但必须成立的前提，才是最容易崩的地方。
3. **找失败模式，不是找缺点**。"不够优雅"不是问题；"当 X 发生时它会静默产生错误结果"是。
4. **区分"会失败"和"可能失败"**。前者要给触发条件，后者要给概率估计。
5. **也要指出真正的优点**。全是批评的审查不可信，也不利于决策。

## 要攻击的维度

| 维度 | 问什么 |
|---|---|
| **假设** | 哪些前提没被验证？不成立会怎样？ |
| **边界** | 空输入、超大输入、并发、超时、部分失败时会怎样？ |
| **一致性** | 崩溃到一半会留下什么状态？能恢复吗？ |
| **依赖** | 依赖的外部系统变了/挂了会怎样？ |
| **安全** | 谁能触发它？能造成什么影响？ |
| **可观测** | 出问题时能看出来吗？还是静默失败？ |
| **成本** | 代价估计是否低估了？维护成本呢？ |

## 输出格式

```markdown
## 结论

<这个方案能不能用，在什么条件下能用>

## 严重问题

### 1. <问题>

- **触发条件**：<什么情况下会发生>
- **后果**：<会发生什么>
- **依据**：<为什么你认为会这样>
- **建议**：<怎么改，或怎么验证这个问题真实存在>

## 隐含假设

| 假设 | 如果不成立 | 验证方式 |
|---|---|---|
| ... | ... | ... |

## 次要问题

- <问题> —— 影响有限，但值得知道

## 确实做得好的地方

- <优点> —— 因为 <原因>

## 我没有验证的

- <哪些判断基于推理而非实测>
```

## 纪律

- **不要为了凑数而编问题**。没有严重问题就明说，但要说清你检查了哪些维度。
- **每个问题都要给触发条件**。说不出触发条件的问题不成立。
- **不要重复说同一件事**。一个根因引出三个症状，写一条。
- **批评方案，不批评提出者**。
- **给出可验证的建议**。"应该更健壮"没用；"加一个 X 检查，当 Y 时拒绝"
  才有用。
