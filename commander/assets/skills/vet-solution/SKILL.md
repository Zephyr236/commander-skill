# 评估外部方案

用户需求原文：「寻找网上的开源项目是否可以直接使用来完成任务的」
「用于寻找agent框架……然后派发去使用」

找到候选只是开始。**真正的工作是判断它能不能接进来、值不值得接。**

## 你要回答的四个问题

按重要性排序。前两个是硬门槛，答不上来就不用往下看了。

### ① 能不能接？（硬门槛）

我们这套系统的接入方式只有三种：

| 方式 | 什么时候适用 | 怎么判断 |
|---|---|---|
| **装成新后端** | 它是个 Python 库，有稳定的编程接口 | 能不能 `import` 它、调一个函数拿到结果？ |
| **当子进程调** | 它是个 CLI 或服务 | 有没有命令行入口？输出能不能解析？ |
| **直接抄做法** | 它太大 / 依赖太脏 / 不兼容 | 它的核心思路能不能用几十行自己实现？ |

**关键约束**：我们的后端是**独立 uv 工程**，所以依赖冲突不是问题。
但如果它**钉死了 pydantic / httpx 的版本**且和引擎冲突，就要权衡。

### ② 能不能用我们的模型？（硬门槛）

大多数 agent 框架默认假设你用 OpenAI。检查：

- 支持自定义 `base_url` 吗？
- 支持非 OpenAI 的模型名吗？
- **有没有强制结构化输出 / function calling**？（兼容端点常常不稳）
- **要不要视觉模型**？（我们默认用文本模型）

答不上来的，去翻它的源码里 LLM 适配层，不要只看 README。

### ③ 维护状态如何？

| 信号 | 好 | 坏 |
|---|---|---|
| 最近 commit | 3 个月内 | 1 年以上没动 |
| issue 响应 | 有 maintainer 回复 | 堆积无人理 |
| 版本号 | 稳定版 / 1.x+ | 长期 0.x 且频繁破坏性变更 |
| 文档 | 有 changelog、有迁移指南 | 只有 README |
| 官方态度 | 活跃开发 | **已声明进入维护模式** |

**明确标注"维护模式"的项目要特别小心** —— 它现在能用，但出问题没人修。

### ④ 引入的代价是什么？

- **依赖重量**：拉进来多少个包？有没有编译依赖？
- **运行要求**：要不要额外的系统级东西（浏览器、数据库、GPU）？
- **license**：能不能商用？有没有传染性（GPL）？
- **和现有架构的冲突**：它是否要求独占某个资源、改全局配置、或接管进程？

## 输出格式

```markdown
## 结论

**建议采用 / 建议不采用 / 建议只抄做法** —— 一句话说清，前置。

## 候选对比

| 项目 | 接入方式 | 维护状态 | 依赖数 | 阻塞点 |
|---|---|---|---|---|
| [a/b](url) | 新后端 | 活跃 | 57 | 需要 Chrome |
| [c/d](url) | 抄做法 | 维护模式 | — | 强制 OpenAI |

## 推荐方案：<名字>

**为什么**：<最关键的一条理由>

**怎么接**：
1. <具体步骤，能照着做>
2. ...

**风险**：
- <接手后会遇到什么>
- <什么条件下这个方案会失效>

## 被否掉的候选

| 项目 | 为什么否 |
|---|---|
| ... | <一句话，要具体> |
```

## 纪律

- **不要罗列功能**。「支持 X、Y、Z」不是评估，是宣传
- **每个判断都要有依据**：哪一行源码、哪个 issue、哪个 commit 日期
- **给出「不采用」也是结论**。找不到合适的就直接说，不要硬凑一个
- **优先考虑「抄做法」**。引入一个外部依赖的长期成本，通常高于自己写 50 行
- **如果它要求视觉模型而我们只有文本模型**，明确说这是阻塞点，不要含糊
